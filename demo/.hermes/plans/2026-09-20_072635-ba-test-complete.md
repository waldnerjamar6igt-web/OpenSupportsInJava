This wraps both `UserMapper` and `StafaMapper` and implements `AccountRepo` interface. Maps methods like:

Wait — re-checking: The Account model has BOTH user fields (email, password_hash) AND staff fields (level, department_id). It appears the design uses a single joined table pattern where all accounts live in `users` and staff-only data lives in `staff` table. The Account class handles both.

1. Find by email → check `users` table; if `level != null` → also load from `staff`
2. Create user → insert into `users`; initAsStaff → insert into `staff`
3. Update → update `users` table fields
4. Delete → delete from `staff` (cascade) then `users`

Implementation approach: Create `AccountRepoImpl` as a Spring bean that uses both `UserMapper` and `StafaMapper` directly.

#### Task 4.5: Fix assignTicket() — permission based on L1/L2/L3

Current logic rejects self-assignment. Per BA.md:
- **L1/L2**: Can only assign to self
- **L3 (admin)**: Can assign to anyone, cross-department

Fix:
```java
@Transactional
public void assignTicket(Long ticketId, Long currentStaffId, AssignTicketCmd cmd) {
    var ticket = ticketRepo.getById(ticketId);
    if (ticket == null) throw new ResourceNotFoundException("Ticket", ticketId);
    
    var staff = accountRepo.findById(currentStaffId);
    if (staff == null || !staff.isStaff()) throw new PermissionDeniedException("必须为员工");
    
    Long targetStaffId = cmd.getStaffId();
    if (targetStaffId == null) targetStaffId = currentStaffId;
    
    if (!staff.isAdmin() && !targetStaffId.equals(currentStaffId)) {
        throw new BusinessRuleViolationException("INVALID_ASSIGNMENT", "只有L3可以分配给他人");
    }
    
    if (!staff.isAdmin() && !staff.getDepartmentId().equals(ticket.getDepartmentId())) {
        throw new PermissionDeniedException("只能分配本部门工单");
    }
    
    ticket.assignTo(targetStaffId, /* need staff name */);
    ticketRepo.save(ticket);
}
```

## Risks, Tradeoffs, and Open Questions

### Risks

1. **H2 compatibility**: SQLite-specific features (`||`, `datetime('now')`, `RETURNING`, `INSERT OR IGNORE`) won't work in H2. If H2 fails, use SQLite temp file mode — much slower startup but accurate to prod.
   - **Fallback**: Use `jdbc:sqlite::memory:` with `@DirtiesContext(classMode = AFTER_EACH_TEST_METHOD)`.

2. **Non-standard Maven structure**: Files under `src/java/` won't be picked up even after mv. Must also remove old `src/java/` entries from IDEA/module configurations. Verify `pom.xml` doesn't have explicit `<sourceDirectory>` overrides.

3. **Session-JDBC schema**: Spring Session requires a `SPRINGSSESSION` table in the test DB. For SQLite, this may need DDL manually executed before tests.

4. **Account model fields**: The Account class (via Lombok `@Data`) expects many fields. Some field names derived from XML result maps (e.g., `signUpTime`, `lastLoginTime`) need to match exactly. If mismatches found during compilation/testing, sync field names.

5. **MyBatis ResultMap type alias**: MyBatis auto-maps `type="com.openSupports.demo.Domain.Model.Ticket"` but needs `typeAliasesPackage` to be scanned. Already set in `application.yaml` line 23.

### Tradeoffs

- **SQLite vs H2**: Testing with exact same engine (SQLite) is more reliable but slower. H2 is faster but risks hidden bugs showing up only in SQLite at deploy time. Recommendation: use H2 for speed, but run occasional `docker run sqlite:latest` validation.

- **Integration tests vs unit tests**: Using SpringBootTest is easier (lives within Spring context, real beans, real DB interactions) but slower. For this backend, integration tests cover the right granularity given the DAO-centric architecture. Unit tests would require mocking every MyBatis mapper, adding complexity without proportional benefit.

### Open Questions

1. **Default department setup**: Should tests seed a default department? BA.md says users cannot choose default department. Tests must create departments explicitly.

2. **Attachment support**: Neither `attachments` table nor `Attachment` domain logic appears wired up in controllers/services. Is attachment upload in scope for this round, or deferred? 

3. **Supervisor role (UC-01/06)**: BA mentions supervisor (L2) viewing supervised user tickets. Is this feature implemented anywhere?

4. **CSRF protection**: BA.md mentions `csrf_userid/csrf_token` business rule for sign-in. Currently unused in login flow. Need to decide: implement or skip for this round?

5. **Event sourcing/domain events**: Domain events are defined (`UserRegistered`, `StaffCreated`, etc.) but never published/listened. Are they expected to trigger side effects, or just record-keeping for now?
